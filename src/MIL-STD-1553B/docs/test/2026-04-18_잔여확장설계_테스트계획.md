# 2026-04-18_잔여확장설계_테스트계획

## 1. 테스트 대상

- `docs/design/2026-04-18_잔여확장설계_설계검토.md`
- 남은 설계 항목을 구현 단계로 옮길 때 필요한 검증 기준

## 2. 테스트 시나리오

1. 실장비 `IVendorChannel` concrete 구현이 callback / polling 차이를 `VendorTransferResult` 하나로 정규화하는지 검증한다.
2. RT ↔ RT planner가 명시적 단계와 time-tag 규칙을 유지하는지 검증한다.
3. 1차 Mode Code 묶음 4종이 각각 정상 / 미지원 경계를 지키는지 검증한다.
4. replay reader가 legacy `v0`와 `schema v1` JSONL을 함께 읽는지 검증한다.
5. WPF가 추가되더라도 CLI / Host / Interop 경계를 침범하지 않는지 검증한다.

## 3. 정상 흐름

- 하드웨어 binding이 현재 `NativeSessionApi -> VendorSdkBusAdapter -> IVendorChannel` 흐름을 그대로 재사용한다.
- RT ↔ RT 단계 trace가 설계한 순서대로 기록된다.
- 1차 Mode Code가 지원 코드로 정상 처리된다.
- JSONL exporter가 `schemaVersion`, `recordType`, `sessionId`, `sequence`를 기록한다.
- replay reader가 v1 line을 DTO로 정상 복원한다.

## 4. 비정상 흐름

- callback 누락, queue overflow, hardware open 실패가 도메인 오류로 매핑된다.
- tranche 밖 Mode Code는 계속 `UnsupportedModeCode`로 처리된다.
- 잘못된 `schemaVersion` 또는 필수 envelope 누락 line은 적절히 거부된다.
- GUI 계층이 native DLL 또는 SDK를 직접 호출하려는 경로를 허용하지 않는다.

## 5. 타임아웃 / 재시도

- 하드웨어 binding에서도 timeout / retry / automatic failover 정책은 계속 `Application`이 주도하는지 검증한다.
- callback 기반 SDK에서 응답 지연이 timeout으로 정규화되는지 검증한다.
- RT ↔ RT planner가 단계별 최소 gap과 추가 지연 규칙을 일관되게 계산하는지 검증한다.

## 6. Bus A/B 전환

- 실장비 binding이 `SelectBus` 의미를 현재 simulator와 동일하게 유지하는지 검증한다.
- timeout 또는 line fault 이후 failover가 기존 health / telemetry 모델을 그대로 따르는지 검증한다.

## 7. BC → RT

- 실장비 binding에서도 BC → RT 요청이 현재 DTO / telemetry 모델을 그대로 유지하는지 검증한다.
- schema v1 event line이 BC → RT `MessageFrame`을 손실 없이 표현하는지 검증한다.

## 8. RT → BC

- 실장비 binding 또는 simulator planner 확장 후에도 RT → BC payload 보존 규칙이 유지되는지 검증한다.
- replay reader가 RT → BC frame payload를 legacy / v1 모두에서 동일하게 복원하는지 검증한다.

## 9. RT ↔ RT

- planner가 destination command, source command, source status-data, destination status 단계를 구분하는지 검증한다.
- 최소 `40us` baseline과 후속 richer timing 규칙이 충돌 없이 공존하는지 검증한다.

## 10. Mode Code

- 1차 Mode Code 4종의 정상 처리, 오류 처리, telemetry 기록을 검증한다.
- 2차 Mode Code는 구현 전까지 여전히 `UnsupportedModeCode`로 남는지 검증한다.

## 11. 로그 확인 포인트

- `MessageFrame`, `BusSwitch`, `AutoFailover` 기본 telemetry 의미가 유지되는지 확인한다.
- schema v1 summary / event line에 `schemaVersion`, `recordType`, `sessionId`, `sequence`가 기록되는지 확인한다.
- RT ↔ RT richer trace가 description 또는 metadata로 구분되는지 확인한다.

## 12. 결과 요약

- 이번 설계는 후속 구현의 검증 기준을 미리 고정하는 문서 작업이다.
- 실제 테스트 실행은 각 구현 사이클에서 수행하고, 이 문서는 그때 사용할 canonical plan으로 유지한다.
