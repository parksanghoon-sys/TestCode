# AGENTS.md

## 저장소 목적

이 저장소는 **MIL-STD-1553B 기반 통신 하네스 엔지니어링** 작업을 위한 프로젝트이다.Codex는 이 저장소에서 항상 다음 전제를 유지해야 한다.

- **C++**: 네이티브 계층, 장치 SDK 어댑터, 버스 프레임 처리, 성능 민감 로직, 시뮬레이터 핵심 처리
- **C#**: 상위 오케스트레이션, UI/CLI, 설정 관리, 시나리오 제어, 리포트, 통합 테스트 도우미
- 전체 구조는 **클린 아키텍처 기반**으로 유지한다.
- 전체 구현은 **객체지향 설계(OOP)** 를 준수한다.
- 문서와 주석은 **반드시 한글**로 작성한다.

## 최우선 작업 순서

이 저장소에서는 아래 순서를 **반드시** 지켜야 한다.

1. **설계 검토**
2. **구현**
3. **테스트**

다음 행위는 금지한다.

- 설계 검토 없이 바로 구현 시작
- 테스트 없이 구현 완료 선언
- 코드만 수정하고 설계 문서/테스트 문서를 갱신하지 않는 행위
- UI, 장치 SDK, 프로토콜 처리, 도메인 판단 로직을 한 클래스에 혼합하는 행위
- 임시 스크립트/하드코딩으로 구조를 우회하는 행위

## TDD 3색 원칙

모든 기능 개발과 버그 수정은 **TDD 3색 원칙(Red → Green → Refactor)** 을 반드시 따른다.

### 1. Red

- 먼저 실패하는 테스트를 작성한다.
- 테스트는 요구사항, 버그 재현, 프로토콜 조건, 타임아웃, 예외 흐름을 드러내야 한다.

### 2. Green

- 테스트를 통과시키는 최소 구현만 수행한다.
- 처음부터 과도한 추상화나 일반화를 하지 않는다.

### 3. Refactor

- 테스트가 통과한 뒤 구조를 개선한다.
- 중복 제거, 책임 분리, 이름 개선, 인터페이스 정리, 의존성 역전 적용을 수행한다.

## 아키텍처 원칙

모든 구현은 **클린 아키텍처 기반**으로 설계한다.

### 권장 레이어

- **Domain**

  - 1553 워드, 메시지, 모드 코드, 타이밍 규칙, 검증 규칙과 같은 핵심 개념
  - 외부 SDK, UI, 파일 시스템, 네트워크 라이브러리를 직접 참조하지 않는다.
- **Application**

  - 시나리오 실행, 명령 흐름, 버스 A/B 전환 정책, 로그 수집 흐름, 테스트 시퀀스 오케스트레이션
  - 유스케이스 중심으로 구성한다.
- **Infrastructure**

  - 장치 벤더 SDK 연동
  - C++ 네이티브 드라이버 어댑터
  - 파일, JSON, 타이머, 프로세스, IPC, 직렬화, 외부 시스템 연동
- **Presentation / Host**

  - C# UI, CLI, 리포트, 운영용 뷰모델/프레젠터
  - 사용자의 입력을 유스케이스로 전달하고 결과를 표시한다.

### 의존성 규칙

- 바깥 계층이 안쪽 계층을 참조한다.
- Domain은 어떤 외부 계층도 참조하지 않는다.
- UI는 벤더 SDK를 직접 호출하지 않는다.
- C#은 가능하면 직접 하드웨어 SDK를 호출하지 말고, **C++ 어댑터 또는 추상화 계층**을 통해 접근한다.

## OOP 원칙

다음을 반드시 지킨다.

- 클래스는 단일 책임을 가진다.
- 인터페이스는 목적이 분명해야 하며 과도하게 비대해지면 분리한다.
- 상속보다 조합을 우선 고려한다.
- `God Class`, 과도한 `static helper`, 절차형 유틸 덩어리를 만들지 않는다.
- 값 객체와 엔터티를 구분한다.
- 상태 변화는 메서드의 의도를 통해 드러나야 한다.
- 예외 흐름은 명확하게 모델링하고, 오류 코드는 의미 있는 타입으로 감싼다.

## 언어별 기본 규칙

### C#

- 프로젝트가 허용하는 범위에서 최신 문법을 우선 사용한다.
- `nullable` 사용을 우선 고려한다.
- DTO는 불변성을 우선 검토한다.
- DI 가능한 구조를 우선 설계한다.
- 인터페이스와 구현을 분리하되, 의미 없는 인터페이스 남발은 금지한다.
- `async/await` 가 필요한 흐름은 취소 토큰과 타임아웃을 함께 고려한다.

### C++

- 가능하면 최신 표준(C++17 이상, 가능하면 C++20) 기준으로 설계한다.
- RAII를 기본으로 하고, 자원 관리는 객체가 책임진다.
- `new/delete` 직접 사용을 피하고 스마트 포인터 또는 값 타입을 우선 사용한다.
- 인터페이스 계층과 장치 SDK 계층을 분리한다.
- 헤더와 구현의 책임을 명확히 나눈다.
- 플랫폼 종속 코드는 Infrastructure로 격리한다.

## 주석 규칙

주석은 **반드시 작성**하며, **XML 형식**으로, **한글**로 작성한다.

### 공통 규칙

- public 클래스
- public struct
- public enum
- public interface
- public 메서드
- public 프로퍼티
- 중요한 private 메서드 중 의도가 복잡한 항목

위 항목에는 반드시 XML 형식 주석을 작성한다.

### C# 예시

```csharp
/// <summary>
/// 1553 상태 워드를 해석합니다.
/// </summary>
/// <param name="word">원본 16비트 상태 워드입니다.</param>
/// <returns>해석된 상태 정보입니다.</returns>
public StatusWord Decode(ushort word)
{
    ...
}
```

### C++ 예시

C++ 표준 문법에 XML 주석이 강제되는 것은 아니지만, 이 저장소에서는 **동일한 XML 스타일 주석 형식**을 사용한다.

```cpp
/// <summary>
/// 커맨드 워드를 파싱합니다.
/// </summary>
/// <param name="word">원본 16비트 커맨드 워드입니다.</param>
/// <returns>파싱 결과 객체입니다.</returns>
CommandWord Parse(std::uint16_t word);
```

## Codex 작업 방식

Codex는 이 저장소에서 다음 순서를 따른다.

1. 먼저 `harness-design-review` 스킬을 사용하여 설계 검토 문서를 작성하거나 갱신한다.
2. 그 다음 `harness-implementation` 스킬을 사용하여 구현한다.
3. 마지막으로 `harness-test-verification` 스킬을 사용하여 테스트, 검증, 문서 갱신을 수행한다.

사용자가 구현만 요청하더라도, 설계 검토와 테스트를 생략하지 않는다.
단, 아주 작은 오탈자 수정처럼 구조 영향이 전혀 없는 작업은 간단한 근거를 남기고 축약할 수 있다.
